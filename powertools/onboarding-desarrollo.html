Montar el entorno para modificar y publicar hooks

De una máquina en blanco a poder publicar un cambio en las dos plantas, con las pruebas en verde. Pensado para quien va a tomar el mantenimiento del sistema.

Lo que hay que saber antes de empezar

El entorno es ligero: Git, Node y Python. No hay base de datos, ni servidor, ni contenedores. La única complicación real es que este repositorio depende de otro —el de reportes— para la sesión con el ERP, y esa ruta hoy está escrita a mano en dos archivos. Se resuelve en el paso 3.

La trampa más común de todo el onboarding

En macOS conviven varios Python. El puente necesita uno que tenga requests instalado, y no siempre es el que responde a python3 en tu terminal. Si un comando falla con “no pude importar steelhead_client: No module named 'requests'”, no está roto el puente: estás llamando al intérprete equivocado. Comprueba cuál tiene la biblioteca e invoca ese explícitamente.

02Traer el código

Son dos repositorios, y la estructura de carpetas importa (ver paso 3).

  1. 1

    Clonar los dos repositorios bajo la misma carpeta padre

    El de Power Tools es el que vas a editar. El de reportes aporta el cliente de conexión y el archivo de credenciales.

    mkdir Ecoplating && cd Ecoplating
git clone <url-del-repositorio-de-power-tools>
git clone <url-del-repositorio-de-reportes>

    Deberías terminar con dos carpetas hermanas dentro de Ecoplating.

  2. 2

    Instalar la biblioteca de Python que usa el puente

    python3 -m pip install requests

    En Windows el comando suele ser py -m pip install requests.

No hay dependencias de Node que instalar

El repositorio no usa paquetes externos: las pruebas corren con el ejecutor que trae Node, y el compilador se descarga en el momento la primera vez que publicas. Por eso no hay un npm install en esta lista.

03Ajustar la ruta al repositorio de reportes

Este paso es obligatorio en cualquier máquina que no sea la original. Sáltalo y todos los comandos del puente fallarán con “no existe”.

Los dos scripts del puente apuntan al repositorio de reportes con una ruta absoluta escrita a mano. Hay que cambiarla por la de tu máquina en ambos archivos:

# sync/lowcode_sync.py  · línea ~38
# sync/maintenance_plans_sync.py · línea ~40

REPORTES_SH_SCRIPTS = Path("/ruta/a/tu/carpeta/Reportes SH/scripts")

Mejora recomendada al tomar el mantenimiento

Sustituir esa constante por una variable de entorno con un valor por omisión —de modo que cada máquina la configure una vez y el archivo deje de cambiar— es una mejora de media hora que elimina este paso para siempre y evita que la ruta de alguien se cuele en el historial. Es el primer cambio recomendado para quien tome el repositorio.

04Primera verificación: las pruebas

Se corren sin credenciales y sin tocar el ERP. Es la forma más rápida de confirmar que el entorno quedó bien.

cd <carpeta-del-repositorio-de-power-tools>
npm test

Deberías ver la lista de casos y, al final, el resumen con todo en verde. Al corte de este documento son 472 pruebas sobre 35 módulos, y terminan en menos de un segundo.

Si esto pasa, el 80 % del entorno está listo

Las pruebas ejercitan toda la lógica de negocio del sistema. Lo único que falta comprobar después es la conexión con el ERP.

05Credenciales y primera lectura del ERP

El puente no tiene credenciales propias: usa las del repositorio de reportes.

  1. 1

    Conseguir el archivo de entorno del repositorio de reportes

    Contiene la cookie y el token de la sesión del ERP. No está en el repositorio —es secreto— y se solicita a quien administra los accesos. Nunca se sube ni se comparte por canales abiertos.

  2. 2

    Leer el catálogo de las dos plantas

    Es una operación de solo lectura: no cambia nada en producción. Si funciona, el entorno está completo.

    python3 sync/lowcode_sync.py list

# y la otra planta
STEELHEAD_DEFAULT_DOMAIN=mty python3 sync/lowcode_sync.py list

    En Windows, la variable de entorno se antepone distinto:

    REM PowerShell
$env:STEELHEAD_DEFAULT_DOMAIN="mty"; python sync\lowcode_sync.py list
  3. 3

    Bajar el estado actual

    Materializa en tu copia local lo que hoy corre en el ERP. Si sale con cambios, alguien editó desde la interfaz.

    python3 sync/lowcode_sync.py pull
git status

Manejo del archivo de credenciales

Nunca lo copies dentro de este repositorio, ni lo pegues en un chat, ni lo dejes en una carpeta compartida. Vive solo en el repositorio de reportes de tu máquina, fuera del control de versiones. Si sospechas que se filtró, hay que rotar la sesión de inmediato.

La regla de las dos copias

Cada regla de negocio existe dos veces: como módulo probado en lib/ y como copia dentro del archivo del hook. No es descuido: el editor de Steelhead recibe un solo archivo y no puede importar nada, así que la copia es obligatoria. La biblioteca existe para poder probar esa lógica fuera del ERP.

El orden correcto, siempre

Primero el módulo en lib/ con su prueba. Después la copia dentro del .ts. Si escribes solo en el hook, esa regla queda sin certificado — y es exactamente donde se cuelan los errores que no dan error.

Restricciones del lenguaje

  • El compilador del editor de Steelhead entiende una versión antigua del lenguaje. La configuración del proyecto la fija para que la revisión local coincida.
  • Si usas sintaxis más nueva, el hook deja de correr sin dar error visible. Es la falla más desconcertante del sistema si no la conoces.
  • La configuración de paquetes está deliberadamente sin declarar módulos globales: hay un archivo de la biblioteca que es del formato antiguo. Cambiarlo rompería ese archivo y su prueba.

07El ciclo de trabajo diario

# 1. partir de lo que corre hoy
python3 sync/lowcode_sync.py pull && git status

# 2. trabajar en una rama propia
git checkout -b feat/lo-que-vas-a-hacer

# 3. editar lib/<modulo>.mjs + su prueba, luego reflejar en el hook

# 4. probar
npm test

# 5. ensayar la publicación sin tocar el ERP
python3 sync/lowcode_sync.py push hooks/<cat>/<archivo>.ts <slug> --dry-run

# 6. publicar en LAS DOS plantas
python3 sync/lowcode_sync.py push hooks/<cat>/<archivo>.ts <slug>
STEELHEAD_DEFAULT_DOMAIN=mty python3 sync/lowcode_sync.py push hooks/<cat>/<archivo>.ts <slug>

# 7. verificar en ambas
python3 sync/lowcode_sync.py diff <slug>
STEELHEAD_DEFAULT_DOMAIN=mty python3 sync/lowcode_sync.py diff <slug>

# 8. registrar en la bitácora del hook y guardar el cambio
git add -A && git commit -m "feat(<hook>): ..."

Los nombres de las ventanillas

Los identificadores que reciben los comandos son de dos formas:

  • Ventanilla única: received-order, invoice, inventory-usage, schedule
  • Ventanilla múltiple: pdf:<TIPO>, file-import:<TIPO>, fee:<ID>

Antes de publicar, la lista de paridad

Ningún criterio que dependa solo de un número interno de catálogo. Los datos de negocio que asume el hook deben existir con el mismo nombre en la otra planta. La lógica nueva debe traer su prueba de anti-regresión. Está detallado en la ficha «Dos plantas, un solo código».

Fin de línea en Windows

Si al clonar ves todos los archivos marcados como modificados sin haber tocado nada, es la conversión automática de fin de línea. Se desactiva con git config --global core.autocrlf false y se vuelve a clonar.

10Lista de verificación del primer día

  • Git, Node y Python instalados, y requests disponible en el intérprete que vas a usar.
  • Los dos repositorios clonados como carpetas hermanas.
  • La ruta al repositorio de reportes ajustada en los dos archivos del puente.
  • npm test en verde.
  • El archivo de credenciales en su lugar, obtenido por canal seguro.
  • Lectura del catálogo funcionando en las dos plantas.
  • Una bajada completa hecha, sin cambios pendientes en el control de versiones.
  • Leídos: el Manual del Administrador y la ficha de paridad.
  • Localizada la bitácora del hook que vas a tocar, y su versión de reversión segura.

Primer cambio recomendado

Algo de bajo riesgo y con recompensa visible: ajustar el texto de un aviso, o corregir el spanglish de las instrucciones de un plan de baño. Te obliga a recorrer el ciclo completo —editar, probar, publicar en dos plantas, verificar, documentar— sin poner en riesgo nada.
